# FastAPI в нашем сервисе

Этот документ — внутренняя шпаргалка по FastAPI: структура проекта, зависимости, стандартные паттерны эндпоинтов, обработка ошибок, и рекомендации по прод‑эксплуатации.

## Почему FastAPI

Мы выбираем FastAPI за:
- асинхронность и высокую производительность на Python;
- автогенерацию OpenAPI/Swagger;
- удобные зависимости (Dependency Injection) для auth/DB/конфигов;
- хорошую интеграцию с Pydantic‑схемами.

## Рекомендуемая структура проекта

Типовой расклад (примерно как у нас):
- `src/routes.py` — регистрация роутов
- `src/handlers/` — обработчики бизнес‑логики
- `src/services/` — интеграции (RAG, файловая система, внешние API)
- `src/database/` — модели/настройки хранилищ
- `src/config.py` — конфигурация (env)

Критерий: эндпоинты тонкие, логика в `services/` и `handlers/`.

## Эндпоинты: базовый шаблон

Минимальный набор:
- входная схема (Pydantic)
- выходная схема (Pydantic)
- явные коды ошибок
- корреляционный `request_id/trace_id` (если есть)

Псевдо‑пример:
```py
from fastapi import APIRouter, Depends, HTTPException
from pydantic import BaseModel

router = APIRouter(prefix="/v1")

class QueryIn(BaseModel):
    query: str

class QueryOut(BaseModel):
    answer: str

@router.post("/query", response_model=QueryOut)
async def query_api(payload: QueryIn):
    if not payload.query.strip():
        raise HTTPException(status_code=400, detail="Empty query")
    return QueryOut(answer="...")
```

## Dependencies (Depends): как использовать правильно

Хорошие кейсы для `Depends`:
- доступ к конфигу (settings)
- доступ к БД/клиентам (Qdrant/Redis)
- auth/ACL
- rate limiting / quota

Правило: dependency должна быть дешёвой и предсказуемой; тяжёлые клиенты создаём один раз (startup) или кешируем.

## Ошибки и исключения

Рекомендации:
- не возвращать «сырые» traceback пользователю;
- унифицировать формат ошибок (код + сообщение);
- различать 4xx (ошибка пользователя) и 5xx (ошибка сервиса);
- логировать `trace_id` и контекст запроса (без секретов).

Если у нас есть общий формат ошибок — используйте его во всех роутерах.

## Валидация данных

Pydantic помогает:
- нормализовать вход (strip, min_length, regex);
- гарантировать типы;
- документировать API автоматически.

Практика: проверяйте ограничения на уровне схемы, а не в теле обработчика, если возможно.

## Производительность (async)

Памятка:
- async полезен, когда есть I/O: БД, сеть, файловая система.
- CPU‑тяжёлые операции (эмбеддинги, большие парсинги) лучше выносить в воркеры/очередь или делать batch.
- не блокируйте event loop синхронными вызовами.

## Запуск в проде

Рекомендуемый стек:
- ASGI сервер: `uvicorn`/`gunicorn` (ASGI workers)
- reverse proxy: nginx/traefik
- health checks: `/healthz` (liveness), `/readyz` (readiness)

Checklist:
- таймауты upstream/proxy согласованы с таймаутами клиентов;
- лимиты на размер тела запроса (особенно для загрузки файлов);
- CORS включён только при необходимости и ограничен по origins;
- включены структурированные логи.

## Наблюдаемость

Минимум:
- логировать: метод, путь, статус, latency, trace_id
- метрики: RPS, p95 latency, 4xx/5xx rate
- трассировка: хотя бы correlation id через весь пайплайн (API → retrieval → LLM)

## Типовые грабли

- **422 Validation Error**: чаще всего неверный JSON или не совпали поля схемы.
- **Зависимости создают клиентов на каждый запрос**: утечки соединений/медленно → используйте кеширование/жизненный цикл приложения.
- **Большие ответы**: стриминг (SSE) или разбиение на чанки, если LLM отдаёт поток.
- **Нет лимитов**: добавьте rate limiting и ограничение concurrent запросов к LLM.
