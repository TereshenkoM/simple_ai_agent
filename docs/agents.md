# Агенты и инструменты

Этот документ фиксирует внутренний «ментальный модель» агента: как он принимает решения, когда вызывает инструменты, как мы проектируем tool‑интерфейсы, и как дебажим типичные сбои.

## Что такое агент

Агент — это LLM‑оркестратор, который:
- принимает задачу пользователя;
- планирует (явно или неявно) шаги;
- вызывает инструменты (поиск, БД, RAG, HTTP, файловая система);
- собирает результаты и выдаёт итог.

В отличие от «чата», агент должен уметь:
- работать с внешним состоянием (база/векторное хранилище);
- проверять себя (например, повторный запрос/валидация);
- объяснять ограничения («нет доступа», «не найдено», «нужно уточнение»).

## Паттерн “Plan → Act → Observe → Answer”

Внутренняя дисциплина, которая снижает хаос:
1) **Plan**: короткий план шагов, критерии успеха.
2) **Act**: вызовы инструментов строго по необходимости.
3) **Observe**: проверка результата, контроль ошибок/таймаутов.
4) **Answer**: итог + ссылки/артефакты (если применимо).

Важно: планы не должны быть «ради планов». Если задача простая — агент отвечает сразу.

## Дизайн инструментов (tools)

Хороший tool API:
- **детерминированный** (одинаковые входы → похожий выход);
- **явные типы** (JSON schema, строгие поля);
- **прозрачные ошибки** (код + сообщение + поле, где сломалось);
- **ограниченный по поверхности** (не даём «всё‑в‑одном» без нужды);
- **идемпотентный**, где возможно (повтор не ломает данные).

### Рекомендуемая форма ответа инструмента

Для большинства инструментов удобно:
```json
{
  "ok": true,
  "data": { "items": [] },
  "warnings": [],
  "debug": { "latency_ms": 0 }
}
```

При ошибке:
```json
{
  "ok": false,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Missing field: query",
    "details": { "field": "query" }
  }
}
```

## Инструменты и безопасность

Базовые правила:
- Любой tool, который может менять состояние, должен быть **явно** помечен как write‑операция.
- Параметры, содержащие секреты, не логировать в чистом виде.
- Для доступа к приватным документам использовать `acl`‑фильтры на retrieval.
- На уровне агента вводить «политику отказа»: если нет прав — честно сообщаем.

## Контекст и память

Разделяйте:
- **короткую память** (текущий диалог, несколько последних сообщений);
- **рабочую память** (артефакты шага: результаты tool‑вызовов, промежуточные вычисления);
- **долгую память** (RAG/БД/профиль пользователя — если продукт это допускает).

Антипаттерн: хранить в «памяти» приватные данные без явного согласия и политики retention.

## Дебаг: типовые симптомы

- **Агент не вызывает нужный tool**  
  Причины: промпт не задаёт ожидания, tool‑описание расплывчатое, нет примеров.  
  Лечение: добавить примеры использования tool, явные триггеры («если нужен факт из БД — вызывай X»).

- **Агент вызывает tool слишком часто**  
  Причины: нет критерия остановки, tool даёт шум, отсутствует кеш.  
  Лечение: лимиты на число вызовов, кеширование, re-rank/фильтры.

- **Путает формат параметров**  
  Причины: слабая схема, неоднозначные поля.  
  Лечение: строгая JSON schema + валидация + хорошие ошибки.

- **Галлюцинации “я выполнил действие”**  
  Причины: tool не возвращает явного подтверждения, модель пересказывает.  
  Лечение: требовать подтверждение из tool‑ответа (`ok=true`) и показывать артефакт (id/ссылку).

## Набор минимальных guardrails

- Лимит tool‑вызовов на ответ (например 3–8, зависит от задачи).
- Таймауты и повтор с backoff для нестабильных инструментов.
- «Кнопка стоп»: если инструмент возвращает опасное действие — запросить подтверждение пользователя.
- Логи: `trace_id`, список tool‑вызовов, latencies, итоговый prompt size.

## Чек‑лист при добавлении нового tool

1) Определить read/write характер операции.  
2) Спроектировать схему входа/выхода.  
3) Добавить примеры вызова и типовые ошибки.  
4) Решить, что логируем и как маскируем.  
5) Добавить минимальные тесты/моки.
